# Release Notes - OpenPDF 4.0.0

OpenPDF 4.0 requires Java 25. It contains everything in [OpenPDF 3.0.7](3.0.7.md), including the security fixes of that release, and uses the Foreign Function & Memory API to release memory-mapped files as soon as they are closed.

OpenPDF 3.0.x for Java 21 is maintained in the [3.0-java21](https://github.com/LibrePDF/OpenPDF/tree/3.0-java21) branch.

## ⚠️ Upgrade Notes
* **Java 25 is required (PR #1685).** The artifacts are compiled for Java 25 and do not run on earlier versions. Stay on OpenPDF 3.0.x if you need Java 21.
* **Everything in the upgrade notes of [3.0.7](3.0.7.md) applies**, in particular the stricter signature verification, the changes to HTML to PDF conversion, and the file offsets that are now `long`.
* **Memory-mapped files are released on close (PR #1686, #1688).**
    * A `LongMappedByteBuffer` must not be used after it has been closed. Doing so throws an `IllegalStateException`.
    * The buffer returned by `RandomAccessFileOrArray.getNioByteBuffer()` for a file is valid until the `RandomAccessFileOrArray` is closed. Before, it stayed valid and kept the file mapped until it was garbage collected. Keep the `RandomAccessFileOrArray` open for as long as the buffer is used.
* **A file is no longer read into memory when it is opened (PR #1691).** An unreadable part of a file is reported by the read that touches it, not when the file is opened.

## 🔒 Security
These fixes are also in [OpenPDF 3.0.7](3.0.7.md).
* **`PdfSmartCopy`:** A small file whose stream dictionaries share objects at several levels no longer makes `PdfSmartCopy` use exponential time and memory (PR #1753).
* **`OpenPdfCoreRenderer`:** A form XObject that draws itself, directly or through other forms, no longer overflows the stack (PR #1755).
* **`OpenPdfCoreRenderer`:** Form XObjects that draw each other very often no longer keep the renderer busy without end. Rendering of a page stops after 20 million operators (PR #1757).
* **`OpenPdfCoreRenderer`:** An image that declares a very large size without having the data for it no longer makes the renderer reserve gigabytes of memory (PR #1759).
* **`OpenPdfCoreRenderer`:** A small JPEG or JPEG 2000 image whose header announces a very large size no longer makes the renderer reserve gigabytes of memory. Such images are only decoded up to 100 million pixels, and only by a JPEG or JPEG 2000 reader (PR #1761).
* **HTML to PDF:** A long run of white space in a text node no longer takes time that grows with the square of its length. The field `WhitespaceStripper.linefeed_space_collapse` is deprecated (PR #1763).

## 🌟 New Features & Enhancements
* **Files are unlocked when they are closed (PR #1686, fixes #1112 and #1517).** Memory-mapped PDF files are mapped with the Foreign Function & Memory API and unmapped as soon as they are closed. On Windows, a file can now be deleted or moved right after `PdfReader.close()`. This is based on the work of Christian Voss in PR #1634.
* **`getNioByteBuffer()` (PR #1688).** The mapping behind `RandomAccessFileOrArray.getNioByteBuffer()` is released by `close()` as well.
* **Faster partial reading (PR #1691).** Opening a memory-mapped file no longer loads the whole file. Reading a PDF in partial mode, where the file is opened again for every stream, was about 8 times faster in a test with a 4,000 page document.
* **Less native memory (PR #1690).** The zlib inflaters and deflaters are closed as soon as they are no longer needed, also when reading or writing fails. In `openpdf-renderer`, the inflater of every Flate stream was only released by the garbage collector before.
* **Renderer:** `OpenPdfCorePageRenderer` supports the text rendering mode (`Tr`), so that invisible text layers of scanned documents are no longer drawn (PR #1603).

## 🛠 Bug Fixes
* **Fonts:** A font family is no longer registered twice in `FontFactoryImp` (PR #1626).

## 🧹 Maintenance & Refactoring
* **Build System:** The CI builds with Java 25, Java 27 and the early access builds of Java 28 (PR #1685, #1687).
* **Code Quality:** Fixed a bug reported by SonarCloud in the copy constructor of `RandomAccessFileOrArray` (PR #1689), and one in the soft mask of `OpenPdfCorePageRenderer` (PR #1765).
